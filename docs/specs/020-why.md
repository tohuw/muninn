# 020 — `muninn why`

**Status:** implemented.
**Read first:** [decisions-outlive-diffs](../../.valholl/articles/decisions-outlive-diffs.md)
for why the reasoning is the part worth keeping; 005-enrichment.md for what
writes `decisions`; 019-recall.md for the sibling retrieval path that also takes
a thing rather than a question.

## Why

`git blame` answers *who changed this line, and when*. Nobody has ever wanted
only that. The question a strange piece of code provokes is **why**, and the
reasoning that produced it happened in a conversation which git never saw.

Muninn holds those conversations, and since spec 005 it holds their `decisions`
as a structured field. Git holds the commits. Neither half answers the question
alone; joined, they do.

## What ships

`muninn why <path> [--limit N] [--decisions N] [--json]`.

For each of the last `--limit` commits touching the path (via `git log
--follow`, so a rename does not truncate the history at the moment the
interesting decision was probably made):

- the commit — sha, date, author, subject
- every session offered as its explanation, strongest first, with topic,
  outcome, summary and decisions

Then, separately, sessions that **edited the file and committed nothing**.

## Attribution, and the tier that was measured out of existence

A session explains a commit when the commit's author date falls inside the
session's lifetime **and** the session touched something relevant:

| Confidence | Meaning |
|---|---|
| `touched-this-file` | the session edited this exact file |
| `touched-this-repo` | it edited something else in the same work tree |

There was a third tier — *open at the time* — and the corpus killed it. Session
length spans four orders of magnitude: median 12 minutes, p90 7 days, p95 27
days, longest 271 days, with 21% open longer than a day. A session parked for a
month overlaps every commit made that month, so **8 sessions were "open" at one
arbitrary commit instant**, of which at most one wrote it. The first live run
duly filed three Cyberpunk-modding sessions under a change to `muninn/cost.py`.

That is not a weak signal worth labelling; it is noise that buries the true
attribution under whatever the user left running. Attribution now requires the
session to have touched something.

**`cwd` is not the repository.** The obvious implementation — match a session's
`cwd` to the work tree — is wrong, and measuring it is what produced this spec.
On the archive it was written against, *zero* sessions had a `cwd` under the
muninn checkout while that repository's entire recent history had been written
from sessions rooted in a sibling one. `cwd` records where an agent was
launched; anyone working across two repositories from one shell breaks it, and
the failure is silent — an empty result that reads like "no history". Touched
files are the honest signal.

## Path matching

The comparison is the repository-relative path **including the repository's own
directory name**, case- and separator-insensitively.

- Not the bare basename: that files a different project's `cost.py` under yours,
  wearing the strongest confidence label the tool has. Worse than a miss.
- Not the tail alone: `pkg/thing.py` exists in any number of checkouts, and a
  test caught exactly that collision.
- Not the absolute path: a checkout at a different root, on another machine or
  platform, would stop matching for no reason a reader could see.

Separator normalisation is load-bearing rather than cosmetic. `git rev-parse
--show-toplevel` answers with forward slashes even on Windows, while the archive
stores whatever the agent's tool call recorded. Comparing them raw matched
nothing, and the repo tier silently reported empty.

## Reading git

Read-only, never through a shell, every path argument after a literal `--` so a
filename can never be read as an option, and a 30-second timeout.

`encoding="utf-8", errors="replace"` is pinned explicitly. `text=True` decodes
with the *locale* codec — cp1252 on a Windows console — and a commit subject
containing an em dash then raises `UnicodeDecodeError`, which is neither
`OSError` nor `SubprocessError` and so escapes every handler written to catch a
subprocess failing. This project has been bitten by that class three times; a
test commits a subject with an em dash and non-ASCII characters.

Any git failure degrades to "no commit history to attribute" with the sessions
still reported. A file outside a work tree is a normal case, not an error.

## Acceptance criteria

1. A session that edited the file and spans the commit explains it, at
   `touched-this-file`, carrying its decisions.
2. A session that only overlaps in time explains nothing.
3. A session that edited a sibling file in the repo explains it at
   `touched-this-repo`; the stronger claim sorts first.
4. A commit outside every session is reported with no session rather than
   omitted.
5. Tool-invoked sessions never explain anything.
6. A same-named file in an unrelated project does not match; the same file under
   a different checkout root does.
7. Sessions that edited the file but produced no commit are reported separately,
   and a session already credited with a commit is not repeated there.
8. A naive timestamp is read as UTC rather than discarded.
9. Outside a work tree: exit 0, both absences named distinctly ("no commits" vs
   "no sessions recorded touching it").
10. A real repository's log is read without a locale decoding error, including a
    subject with non-ASCII characters.

## Out of scope

- **Line-level attribution.** `git blame -L` gives a line its commit; this
  explains the commit. Threading line ranges through adds precision the
  underlying session data cannot support — a session's decisions describe the
  session, not a hunk.
- **Writing anything.** Read-only, like every other retrieval path here.
- **Fetching, or any network git operation.** Local history only.
